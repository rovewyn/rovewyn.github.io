SUBSTRATE / BROWSER CAPACITY

How many browsers
fit on a laptop?

I increased the number of browser Actors and the task arrival rate. Then I paused the Actors and sent a new task burst.

One experiment Worker ran 16 browser Actors. A 5-minute run at 8 Tasks/s met the Task time target. SuspendActor and ResumeActor preserved the checked page values in the concurrent and burst runs.

TASK DEFINITION

One Task

One Task uses one Actor and makes four MCP tool calls, in this order.

01 / ACTOR COUNT

Adding more browsers to one Worker

I tested how adding more browser sandboxes changed Task speed, CPU use, and memory use. Each Actor ran one browser sandbox. I tested two sets of limits per Actor: 2 CPU and 2 GiB of memory, or 0.5 CPU and 1 GiB of memory. I increased the Actor count in steps for each setup.

A Worker is the Kubernetes Pod that runs the Actors. This experiment used one Worker with an 8 CPU limit and a 16 GiB memory limit.

02 / ARRIVAL RATE

Task throughput and queues with 16 browsers

I kept the number of Actors at 16. Each Actor had a 0.5 CPU limit and a 1 GiB memory limit. I changed how many Tasks I submitted each second.

Submit Tasks for 30 seconds.

  1. I tested 1, 2, 4, 8, and 12 Tasks/s. At each rate, I ran two tests. In each test, I submitted Tasks for 30 seconds.
  2. I submitted Tasks at regular intervals. I did not wait for one Task to finish before submitting the next. At 8 Tasks/s, I submitted one Task every 125 milliseconds.
  3. I sent Tasks to the 16 Actors in turn. Different Actors could work at the same time, but each Actor ran one Task at a time. If an Actor was busy, its next Task waited in its queue.
  4. After 30 seconds, I stopped submitting Tasks and waited for all remaining Tasks to finish.

I measured how many Tasks finished per second, how long they waited in a queue, and their total time. Total Task time includes that wait. To pass, p95 Task time had to be 5 seconds or less, with no failed Tasks. All remaining Tasks also had to finish within 5 seconds after I stopped submitting new ones.

Hold the rate for five minutes.

I chose 8 Tasks/s because it was the highest tested rate that passed both 30-second tests. I then submitted Tasks at this rate for 5 minutes. I used the same 16 Actors, resource limits, and queues. After 5 minutes, I stopped submitting Tasks, waited for the remaining Tasks to finish, and checked the same pass criteria.

03 / SUSPEND AND RESUME

Time to suspend and resume browser Actors

Purpose

This test checks whether several browser sandboxes can pause and resume together while keeping their web pages intact. It also measures how long this takes, how much memory it uses, and how much snapshot data moves through storage.

What I did

I tested groups of 1, 4, 8, and 16 Actors, with one browser in each Actor. Each Actor had a 0.5 CPU limit and a 1 GiB memory limit. At each group size, every Actor first ran one Task to open its page and enter and save text. I then repeated this cycle three times:

  1. Record the page state. Read each page's start time, random JavaScript memory value, counter, input text, and saved note.
  2. Pause the group. Call SuspendActor for all Actors in parallel. Wait for every call to finish, then measure the space used by their snapshots.
  3. Wait 2 seconds.
  4. Resume the group. Call ResumeActor for all Actors in parallel. Read the existing pages through the same MCP sessions and compare their state with the saved records.

The three cycles ran one after another, using the same pages. Suspend time includes creating and saving the snapshot. Resume time includes restoring the Actor and reading its page state.

How to read the charts

The horizontal axis shows the number of Actors in the group. Use the buttons to choose a measurement:

  • Per Actor: the median time for one Actor to pause or resume.
  • Whole batch: the time until the last Actor in the group finishes, shown as the median of the three cycles.
  • Peak memory: the highest sampled memory use of the Worker and the whole Kubernetes node.
  • Snapshot transfer: data uploaded to and downloaded from RustFS, the snapshot store, during a cycle.
  • Disk I/O: data that RustFS actually reads from and writes to disk during a cycle.

What I found

Substrate's README claims resume operations below 500 ms. In my 8-Actor test, the median per-Actor suspend command took 3.32 s, and resuming and reading the page took 3.39 s. The resume command alone took 2.72 s. Removing the page check still leaves a result measured in seconds. The README's 500 ms claim refers to resume operations.

I timed the entire kubectl-ate command: process startup, a new port-forward, authentication, the TLS connection, the lifecycle request, and cleanup. The resume-to-page-read timer also included the MCP page check. The official benchmark separates server-side RPC time from client round-trip time, and also reports snapshot restore time. I did not measure those parts separately. This setup did not show sub-second end-to-end resume; the measurements do not identify which part accounts for the difference.

04 / IDLE TIME AND BURSTS

Memory savings and the next Task burst

Purpose

This test measures the memory saved by suspending idle browsers and the delay when work starts again. It also checks whether their pages keep unsaved text and added page elements.

What I did

I used 16 Actors, with one browser in each Actor. Each Actor had a 0.5 CPU limit and a 1 GiB memory limit. I repeated the same steps three times with these Actors:

  1. Prepare the pages. Each Actor ran one Task. I then added an unsaved draft and a new page element and recorded the page state.
  2. Leave the browsers running for 10 seconds. Submit no new Tasks and measure memory while the browsers are idle.
  3. Pause the group. Call SuspendActor for all 16 Actors in parallel. Wait for every call to finish, then measure snapshot disk space.
  4. Keep the group suspended for 20 seconds. Measure memory during this period.
  5. Start the burst timer and resume the group. Call ResumeActor for all Actors in parallel, then read their existing pages and compare the recorded state.
  6. Send the next work. After all page checks finish, send one Task to each Actor. The 16 Tasks run in parallel. Each Task's timer ends when its screenshot tool returns.

The cycles ran one after another. Burst Task time starts when the group begins resuming. It includes the resume commands, all group page checks, and the Task's four MCP calls.

METHOD AND RECORDS

What I ran.

Task records

I recorded submission time, the four MCP call times, queue time, and success or failure. Each Task replaced the previous screenshot file.

Screenshot retrieval and result checks occurred after Task timing. Each Actor waited for these checks before starting its next Task.

Page values

After ResumeActor, I read each existing web page through its MCP session. I compared its start time, a random value in JavaScript memory, counter, input text, and saved note.

In 04, I also compared an unsaved draft and an added page element.

Task time
Time from scheduled submission until the screenshot tool returns. Includes queue time and all four MCP calls.
Queue time
Time from scheduled submission until the first MCP call starts.
Throughput
Successful Tasks divided by the full elapsed time. The green arrival-rate line counts Tasks completed during the two 30-second submission periods.
Suspend time
Time from starting SuspendActor until the command finishes. Includes creating and storing the snapshot.
Resume → page read
Time from starting ResumeActor until the existing MCP session returns the page values.
Burst Task time
Time from starting ResumeActor until that Task's screenshot tool returns. Includes restoring Actors, checking all pages, and the four MCP calls.
CPU
Average CPU cores used, calculated from Linux CPU time. A value of 1 means one core was fully used during the measured period.
Memory
Worker or node memory, measured with Linux cgroup counters about once per second. Includes execution memory and file cache.
Execution memory
Anonymous memory + shared memory + kernel memory. gVisor accounts application memory as shared memory.
File cache
File memory minus shared memory. Linux includes shared memory in its file-memory counter.
Snapshot transfer
Bytes uploaded to and downloaded from RustFS, the snapshot store, during a complete suspend and resume cycle. Includes HTTP traffic and object metadata.
Snapshot disk space
Disk space allocated to the latest snapshot. I measured allocated blocks with du -sk.
Disk I/O
Bytes read from and written to disk during a cycle. Reading cached data does not require another disk read.
p95
The 95th percentile of measured times. About 95% of the times are at or below this value.
Pass criteria
For Tasks on running Actors: p95 time ≤ 5 seconds and no failures. The 30-second and 5-minute submission tests also had to finish remaining Tasks within 5 seconds after submissions stopped.

The Kubernetes node hosts Workers and shared services. Kind ran this node in a Docker container.

Each Actor used one simple local page. Image files were already cached. The Tasks used no model API.

Run durations, counts, and operation record

I retained the original browser resources. The experiments used a separate WorkerPool and two Actor templates. The experiment Actors were suspended after the runs. Their snapshots remain local.
