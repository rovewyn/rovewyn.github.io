A browser that wakes up
where it left off.

Motivation

A browser agent waits for model responses, human decisions, and new tasks. Chromium continues to use memory during these waits. Closing Chromium releases its execution memory. Reopening the URL does not restore unsaved text, JavaScript objects, or the original page state.

I tested whether Substrate could preserve this state. Substrate uses Actors as durable execution instances. A Worker hosts an Actor while it runs. Substrate can suspend an Actor and resume it on an available Worker. A snapshot stores Actor state for later restoration.

This experiment used gVisor to capture process state. PostgreSQL stored control state. RustFS stored snapshots.

The page retained its memory objects, unsaved text, added page element, and page start time after Worker replacement. I clicked the page again. The counter continued from its previous value. These observations support recovery of the existing web pages in this runtime and workload.

Observed behavior: suspension stored the browser's execution state in a snapshot. ResumeActor restored that state after a delay. The supporting services continued to use resources. The next experiment must measure the total cost under agent traffic.

Configuration

I built an ARM64 image with Node, headless Chromium, Playwright MCP, and a local HTTP page inside the Actor. An external client used Model Context Protocol (MCP) tools to control the browser. I tested navigation, text input, clicks, JavaScript, screenshots, and tabs. Scripts controlled the workload. The test did not require a model API key. Chromium produced screenshots in headless mode.

Page state

A page can reload and still look the same. Cookies can also survive a reload. A screenshot or cookie alone cannot show that a web page kept its state.

I created a random proof object in JavaScript memory. I entered text without saving it. I added an HTML element to the page after page load. I also recorded performance.timeOrigin and a counter stored only in memory.

After SuspendActor, I did a check of the recorded snapshot fidelity. It was SNAPSHOT_FIDELITY_MEMORY. I verified that the original Worker served no other Actor. Then I deleted its Pod.

I waited for the replacement Worker to become ready and register with Substrate. After ResumeActor, I reused the original MCP session to read the existing pages. During this comparison, I did not navigate or insert replacement state.

In the Substrate API definition, preferred snapshot fidelity sets an upper limit. Substrate can save less state, including when the host has insufficient resources. A successful ResumeActor call does not confirm memory continuity. This check required a memory snapshot and matching page state held in memory.

Latency

The lifecycle test used one primary Actor with two simple local tabs. Each cycle suspended the Actor, resumed it, read both pages, and clicked once. All ten state comparisons passed. The primary counter increased from 100 to 110.

I collected separate Chromium launch samples with temporary Actors. These Actors started from a template snapshot that had no running browser. The primary Actor remained present during the launch tests.

Timing boundaries: browser launch timing starts at navigation, after Actor resume and MCP initialization. Resume-to-state-read timing includes the ResumeActor CLI call and the first successful read of both existing tabs. The measurements cover different operations. They cannot establish a general speed improvement.

Resources

The two values measure different resources. A cgroup is a Linux resource accounting group. Its memory value includes gVisor, guest processes, caches, and kernel structures charged to the Actor. I sampled the 326 MiB value after resume. I did not measure peak memory during suspension or restoration.

Substrate compresses the state stored for restoration. The shared browser image remains available to the Workers. Each snapshot does not include another copy of its 1.743 GiB uncompressed image. To measure snapshot disk allocation, I multiplied du -sk output by 1024. This value includes filesystem metadata as well as stored data.

gVisor's checkpoint documentation describes compression and options that omit committed memory pages filled with zeros. A sparse file can represent empty ranges without allocating disk blocks for them. Thus, logical file size, disk allocation, compressed data size, and resident memory can differ. This experiment did not measure each mechanism separately. It also did not measure how much runtime overhead the snapshot excluded.

After a later suspension, the previous Actor cgroup contained no processes. It recorded zero anonymous, shared, and file memory. It retained 4 KiB of kernel metadata. Worker Pods, the control plane, the database, and snapshot storage still used resources. A separate active/idle test must measure savings for the whole cluster.

I also tested a Go counter whose state existed only in memory. After Worker replacement, the counter retained its value of 42 and the same process identity. The next request increased it to 43.

Actor memory was 67.23 MiB. The compressed memory-page object was 4.19 MiB. Snapshot disk allocation was 4.31 MiB. Snapshot size therefore cannot replace a measurement of memory used while the Actor runs.

Runtime

In earlier attempts, Node and MCP resumed, but Chromium was unusable after restoration. I retained these failures in the operation record. I excluded them from the successful samples. A later attempt stopped before the replacement Worker completed registration. Worker readiness and registration with Substrate are separate conditions.

The official ARM64 PAC checkpoint/restore issue reports a problem with pointer authentication keys. On systrap, these keys do not survive restore. The merged temporary mitigation disables PAC on systrap. I deployed a separate browser runtime configuration with the official release-20261005.0 binaries. The workload then passed.

This result is consistent with the documented issue. I did not isolate the instruction that caused my browser failure. The result applies to the fixed Chromium version, gVisor release, and simple pages used here. Other OCI images and browser workloads require separate tests.

Operation record

  1. I configured Docker Desktop. I created a separate Kind playground with one node, a local registry, and a project kubeconfig. I deployed Substrate core services, Counter, and Sandbox from the fixed upstream commit.
  2. I did a check of Counter memory and file continuity. I did a check of Sandbox file persistence. I deleted the original Worker of the Go process with memory-only state. I resumed that process and compared its state.
  3. I built the browser image. I deployed two browser Workers and an ActorTemplate with a memory snapshot. I tested navigation, input, clicks, JavaScript, screenshots, and two tabs.
  4. I recorded the failed restoration attempts. I read the official ARM64 runtime issue. I updated the browser runtime configuration.
  5. I created page state held in memory. I invoked SuspendActor. I deleted the original Worker after verification that it served no other Actor. I invoked ResumeActor. I compared the existing page state without navigation.
  6. I collected ten separate browser launch samples and ten sequential SuspendActor/ResumeActor cycles. I tested external HTTPS and a standard MCP SDK client. I stopped and started the full playground.

The experiment repository at a19d53a contains the image recipe, manifests, dependency lockfiles, and scripts. The commands below use the current script locations and Substrate operation names:

# From a prepared substrate-browser-lab checkout
./experiments/browser/browser.sh verify
./experiments/browser/browser.sh suspend-resume
./experiments/browser/browser.sh benchmark --iterations 10
python3 experiments/browser/scripts/restart-check.py

The first command resets the shared browser context. Later commands can delete a Worker Pod or restart the Kind node owned by this experiment. The original Worker replacement command was named checkpoint. During repository import, I renamed it suspend-resume. I have not rerun the scripts from their new locations against the live cluster.

Dependency lockfiles fix the npm package versions. Rebuilding Debian packages can produce different image bytes.
